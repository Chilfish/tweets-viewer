# 006-X 拒绝数据中心出口 IP（daily fetch 全量 403）

## 摘要

每日定时更新里 18 个用户全部 `403 Forbidden`，job 显红。真实原因是 **X 拒绝 GitHub runner 的出口 IP**（数据中心段），与 API Key 无关；但当时的日志只有 `status: 403`，很容易被读成「cookie 过期」。修复是把抓取出口换成代理节点，并补上 401/403 的 Key 轮换与错误明细日志。

## 影响

- 范围：`fetch-daily.yml` 每日定时抓取的 Twitter 部分；当次数据断更一天
- 代价：单次运行约 **4.5 分钟**全部耗在「18 用户 × 5 次退避重试」上，零成功；排查期间一度得出**错误结论**并据此推进过方案（见时间线第 3 步）

## 时间线

1. `run 34775123646`：`action: "fetch-timeline-error", status: 403`，18 个用户各重试 5 次后跳过，退出码 1，按设计自动开 issue #10
2. 用 `.env` 里同一批 Key 在本地打同一接口 → 全部成功；查历史 100 次运行只有这一次是 403（上一次失败是 runner 抢不到，无关）；`TWEET_KEYS` secret 在失败前 3 小时刚更新 → 判定与 Key 无关，是出口问题
3. 逐节点验证代理节点时曾给出「hysteria2 可用、anytls/vmess 不可用」的结论 —— **随后被自己推翻**：本机跑着 Clash TUN，测试实例的 DNS 被外层 fake-ip 接管（日志 `[DNS] a.mjanyt.com --> [198.18.0.9]`），出站又被二次转发，**逐节点结果全部不可信**（成功的那两个也可能是外层节点在同 IP 池里的假象）
4. 改用 check-host 从全球 8 个探针做**端口级**验证：机场 TCP 端口 8/8 可达 → 排除「机场只允许中国来源」
5. 在 **runner 上**用临时 probe workflow 逐节点实测 → **7/7 全部可用**（含走 UDP 的 hysteria2），确认「把出口换成节点」即可解决
6. 合并 PR #11 后在分支上实跑真实 daily job（`run 34778050003`）→ **18/18 用户成功**，耗时约 1 分钟

## 根因

- 直接原因：GitHub runner 的出口 IP 被 X 判定不可信，返回 403。Rettiwt 每次请求前都要先抓 `https://x.com/home` 生成 `x-client-transaction-id`（`FetcherService.ts:109`），挑战页会连锁导致后续全部请求 403
- 系统条件一：错误日志只记录 `status`，不记录 X 返回的明细（`TwitterError.details`，如 `code 32`）。「出口被拦」和「凭据失效」在日志上完全同形
- 系统条件二：`RettiwtPool` 的换 Key 策略只覆盖 429 —— 一把不可用的 Key 会让 18 个用户**全部**失败，且每次都要把 5 次退避跑满
- 系统条件三：本机验证环境自带代理（TUN + fake-ip），在没确认「进程实际解析到/连到了什么」之前就采信了逐节点结果
- 根因归类：`工具反馈滞后`（日志缺明细 + 本地测量被环境污染）为主，`设计建模`（错误分类与轮换策略不完整）为辅

## 行动项

- [x] 抓取出口经代理：`fetch-daily.yml` 起 mihomo sidecar（二进制按版本缓存、配置来自 `MIHOMO_CONFIG_B64`、节点用 `PROXY_NODE` 固定、起不来直接失败而不是跌回直连）
- [x] `RettiwtPool`：401/403/429 统一视为 Key 级失败 → 轮换 Key → 轮完抛类型化错误（`RettiwtAuthError` / `RettiwtRateLimitError`，携带 `status`，原始错误挂在 `cause`）
- [x] `fetch-tweet-daily`：错误日志补 `details`（类型化错误取 `cause.details`）；Key 级失败一次就中止本轮，不再逐用户重试

## 复盘

- **跨环境链路问题必须在目标环境里验证。** 本机有 TUN/系统代理时，「经代理访问 X」的任何结论都不可信 —— fake-ip 与二次跳转都会给出假结果。要么去目标环境跑，要么先证明进程实际解析/连接的目标是什么。
- **外部 API 拒绝时，先把对方的错误明细落进日志。** 只有 HTTP 状态码时，「出口被拦」和「凭据失效」长得一模一样，会把人引向完全错误的方向（这次差点按「Key 过期」处理）。
- **重试/轮换策略要按错误类别分类。** 只覆盖 429 的轮换策略会把单点故障放大成全体失败：3 把 Key 里坏 1 把 = 18 个用户全挂。
- **先确认测量有效，再投入方案。** 这次差点因为一个自洽但错误的中间结论去搭一套 Cloudflare 代理 —— 而 CF Worker 既不能做 CONNECT 隧道（Workers 无法接受入站 TCP），出口又是同类数据中心 IP，投入方向本身就是错的。
