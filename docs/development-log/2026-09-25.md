# 2026-09-25

## 同步 anonTweet 的 rettiwt-api 数据层 + X Space 卡片

anonTweet 那边修完 X 前端迁移（`e289f96`）并加了 Space 卡片（`6aeb6c45`）后，把两边**同名但独立演化**的
rettiwt-api fork 对齐：补上本仓缺的 JetFuel 解析与 Space 请求，并把 Space 卡片端到端移植过来。

**背景（为什么要另打一次端点）**：Space 推文的 `card.name` 是 `…:audiospace`，`binding_values` 只有
`tweet_id` / `id` / `card_url`，没有标题与图片 —— 会被 `mapTwitterCard` 的最终校验整块丢弃。
所以改动前这类推文正文只剩一个裸 `t.co` 链接，用户无法区分「没做这个功能」和「这个 Space 没了」；
标题 / 主播 / 人数 / 时长全在 GraphQL `AudioSpaceById` 里。

**rettiwt-api（数据层）**

- **JetFuel**：新增 `parsers/jetfuel.ts`（payload → `TrendingCardInfo`），`mapTwitterCard` 增第二个入参、
  解析失败回退 `unified_card`；`details()` 打开 `responsive_web_jetfuel_frame`（上游回传附件的前提）；
  `parseUnifiedCard` 升级为兼容 `media_with_details_horizontal` 布局、domain 取 `url_data.vanity`、
  且只覆盖非 `undefined` 字段（避免 `description` 被清空）。
- **Space**：采用 anonTweet 的 `AudioSpaceById` 请求（queryId `HPEisOmj1epUNLCWTYhUWw`，固定
  `withReplays: true`）；新增 `SpaceDetails` / `EnrichedTweet.space` 与 `helper/space.ts`
  （卡片识别、id 双通道解析「卡片 binding → 正文链接」、元数据映射、可注入的 `attachSpaceDetails`）。
- **取数**：`TwitterAPIClient.fetchSpaceDetails` + 各抓取入口（`fetch-tweet-daily` / `fetchTimeline` /
  `fetchSearch` / fukuoka 研究脚本）在富化后挂载 `space`，随 `jsonData` 落库。
  取数失败（429 / 网络）**不挂**、不伪造墓碑 —— 否则会把限流误报成「已删除」。

**web-react（展示层）**

- 新增 `TweetSpaceCard`（五态：可回放 / 直播中 / 尚未开始 / 不可回放 / 已删除墓碑），挂到 `TweetNode`；
  正文在卡片渲染成功时不再重复渲染同一个 Space 链接，拿不到元数据时链接照常显示。
- 展示层纯逻辑（时长/日期/人数格式化、可播放状态解析、Space URL 判定）放
  `apps/web-react/app/lib/space.ts`：web-react 对 rettiwt-api **只做 type-only 导入**，运行时导入会把
  `RettiwtConfig` 的 `node:http/https` 拖进浏览器 bundle（实测 jsdom 单测直接报
  `No such built-in module: node:`，构建也会带 externalize 警告）。

**取舍与偏差**

- 只整文件覆盖了 `requests/Space.ts`：本仓 fork 在其它同名文件上是**超集**（`TwitterAPIClient` /
  `TweetEnrichmentService` / `RettiwtPool` / history / post-note 等），整体覆盖会删功能并打破
  `apps/scripts` 的导入，故其余一律增量修改。
- 既然请求固定了变量集，顺手清掉失效的 `withReplays` / `withListeners` / `isMetatagsQuery`
  （`FetchArgs` 字段 + `ISpaceDetailsOptions` + CLI flag），避免留下「改了没反应」的开关。
- **历史数据不回填**：旧推文的 `jsonData` 没有 `space`，卡片只在新抓取的推文出现（已登记 backlog）。
