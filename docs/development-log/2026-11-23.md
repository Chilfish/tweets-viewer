# 2026-11-23

## 定时任务不再每日跑 IG，推文抓取改为有界并发

22 日那次运行（`45073013903`）耗时 12m58s，但**推文阶段只用了 39 秒**：`21:36:22` 起跑，`21:37:01` 两个库都打出 `tweet-daily-complete`，18 + 5 个用户全部成功。剩下 11 分钟全在 IG：15 个账号串行跑，每个都被 `Rate limit exceeded (code 1675004)` 顶回来，再各自重试约 50 秒。

之前把失败归因成 Cookie 过期是错的，22 日已经确认是 IG 对数据中心出口的风控（替代代理后错误从「未登录」变成明确限流码）。既然换节点也没通过，每日自动同步就没有收益，只把整轮任务拖成 10 分钟并必然显红。

### IG 改为手动开关

- `dailyUpdate.ts` 的 IG 步骤从「有 `INSTAGRAM_COOKIES` 就跑」改成「`DAILY_INS=1` 才跑」，缺省跳过。
- `fetch-daily.yml` 的 `workflow_dispatch` 加 `ins` 布尔输入，`DAILY_INS` 由它推导：定时运行拿不到 inputs，值为空 → 关闭；手动触发可勾选。
- 日常补数据仍走 `bun run ig ins sync`，和定时任务共用 `syncInsAccounts()`。

### 推文抓取的有界并发

原来按用户串行，3 个 Key 只有 2 路在用（两个库各一路），单用户内部还要串行翻页，Key 基本闲着。改为：

- **用户级并发**：`SYNC_CONCURRENCY` 覆盖，缺省 `Key 数 × 2`（3 Key → 6）。抓取是等代理往返的延迟密集型任务，并发高于 Key 数不会超配额，429 由 `RettiwtPool` 的冷却轮换兜住。
- **进程级闸门**（`createConcurrencyGate`）：多库并发时共用同一个 Key 池，没有闸门就会叠成 `库数 × 并发数`。闸门做成模块级单例，总在飞请求恒为 `SYNC_CONCURRENCY`。
- **Key 级中止是全局的**：`globalAbortReason` 命中后所有库停止派发新用户，已在跑的用户把当前请求做完（不中途打断请求）。

用户内部仍是「刷新资料 → 翻页抓取 → 入库」的串行流程，语义没变；并发只发生在用户之间。
