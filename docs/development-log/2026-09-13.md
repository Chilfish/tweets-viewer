## 定时任务异常处理修正：`fetch-tweet-daily` 静默 0 数据

`apps/scripts/src/fetch-tweet-daily.ts` 的 `fetchTimeline` 自带 `try/catch` 吞掉所有错误并返回空数组，导致外层重试循环的 `catch` 成为死代码：请求失败（如 404）被误判为「无推文」，`fetchOk` 仍被置为 `true`，日志记录 `tweetsCount: 0 / attempt: 1`，进程以 0 退出——每日定时任务静默拉取 0 条也不报错。

对照 `fetch.ps1` 以 exit code 为契约的做法（104 无数据 / 129 限流中止 / 其它非 0 重试＋退避），重写异常处理：

- **不再吞错**：`fetchTimeline` 失败直接向上抛；「时间线为空」仍是合法的成功分支（`fetch-timeline-empty`），与请求失败区分开。
- **重试真正生效**：每次重试从首页重新拉取（避免半截数据叠加成重复），失败按指数退避（1s / 2s）重试，最多 3 次；`catch` 改为类型安全的 `unknown`。
- **限流快速中止**：429 / 全部 Key 耗尽时中止本轮抓取，不再对剩余用户继续打限流。为此在 `RettiwtPool` 新增 `RettiwtRateLimitError`（携带 `status = 429`），取代原先的裸 `Error`。
- **失败显性化**：单个用户重试耗尽后计入 `failedUsers`；只要有失败，结束时不抛异常（不阻断随后的 IG 抓取），而是设 `process.exitCode = 1`，让 GitHub Actions 显红而非假成功。
- **DB 写入错误**：第二阶段 `catch` 同步改为 `unknown` 类型安全（原为 `catch (error: any)`，违反 Key Conventions）。

- `bunx tsc --noEmit -p apps/scripts/tsconfig.json` ✅（仅剩既有 `exportTweets.ts:91` 类型问题，与本次无关）

## CI：Node 20 弃用对齐 + 失败通知修正

排查 `fetch-daily.yml` 一次「绿色但实际失败」的定时运行（run `34710446696`）后发现两个问题：

   - `actions/checkout@v4 → @v5`（v5 起 `runs.using: node24`），三个 workflow 全量替换。
   - 删除 `fetch-daily.yml` 中位置错误的 `FORCE_JAVASCRIPT_ACTIONS_TO_NODE24: true`（放在 run step 的 env 里对其他 action 无效；且 Node 24 已是默认）。

## API：接入 OpenAPI 3.1 规范与 Scalar 文档

为 `apps/server` 接上可交互的 API 文档。

**方案取舍**：Nitro 内置的 `experimental.openAPI` 依赖扫描「文件路由」里的 `defineRouteMeta`，而本项目真实接口全部定义在 Hono 子路由（`index.ts` 用 `.route()` 挂载），Nitro 只能看到 `routes/*.ts` 对应的 4 个顶层路径（`/tweets`、`/users`…），无法覆盖 `/v3/tweets/get/:name` 等真实路径。因此改用 **Hono 原生 OpenAPI**：`hono-openapi`（`describeRoute` + `openAPIRouteHandler`）+ `@scalar/hono-api-reference`。

- **端点**：`GET /openapi.json`（OpenAPI 3.1 JSON）、`GET /scalar`（Scalar UI，CDN 渲染），**生产（Cloudflare Workers）同样可访问**。
- **不改校验契约**：仅新增 `describeRoute` 文档中间件，保留既有 zod 手工校验与 `{ error }` 错误响应（测试锁定的空 cursor→400 等行为不变）。
- **复用层**：`apps/server/utils/openapi.ts` 集中放 query/path 参数构造器、响应 `$ref` 助手、`components.schemas`（19 个：分页信封、IG 模型、Enriched* 松散对象、YearStat、图片等）与文档元信息。类型从 `GenerateSpecOptions` 推导，未引入 `openapi-types` 直依赖。
- **覆盖**：13 个端点、5 个 tag。
- **放置位置**：文档模块放 `utils/` 而非 `routes/`——`routes/` 会被 Nitro 当作文件路由扫描，塞入非 handler 文件会污染路由表。
