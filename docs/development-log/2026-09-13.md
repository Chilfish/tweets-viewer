## 定时任务异常处理修正：`fetch-tweet-daily` 静默 0 数据

`apps/scripts/src/fetch-tweet-daily.ts` 的 `fetchTimeline` 自带 `try/catch` 吞掉所有错误并返回空数组，导致外层重试循环的 `catch` 成为死代码：请求失败（如 404）被误判为「无推文」，`fetchOk` 仍被置为 `true`，日志记录 `tweetsCount: 0 / attempt: 1`，进程以 0 退出——每日定时任务静默拉取 0 条也不报错。

对照 `fetch.ps1` 以 exit code 为契约的做法（104 无数据 / 129 限流中止 / 其它非 0 重试＋退避），重写异常处理：

- **不再吞错**：`fetchTimeline` 失败直接向上抛；「时间线为空」仍是合法的成功分支（`fetch-timeline-empty`），与请求失败区分开。
- **重试真正生效**：每次重试从首页重新拉取（避免半截数据叠加成重复），失败按指数退避（1s / 2s）重试，最多 3 次；`catch` 改为类型安全的 `unknown`。
- **限流快速中止**：429 / 全部 Key 耗尽时中止本轮抓取，不再对剩余用户继续打限流。为此在 `RettiwtPool` 新增 `RettiwtRateLimitError`（携带 `status = 429`），取代原先的裸 `Error`。
- **失败显性化**：单个用户重试耗尽后计入 `failedUsers`；只要有失败，结束时不抛异常（不阻断随后的 IG 抓取），而是设 `process.exitCode = 1`，让 GitHub Actions 显红而非假成功。
- **DB 写入错误**：第二阶段 `catch` 同步改为 `unknown` 类型安全（原为 `catch (error: any)`，违反 Key Conventions）。
