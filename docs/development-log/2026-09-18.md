# 2026-09-18

## 每日抓取顺带刷新用户资料（`fetch-tweet-daily`）

`fetch-tweet-daily.ts` 此前只 upsert 推文，**用户资料是入库时的一份快照**：粉丝数、bio、推文总数、
头像/横幅、认证状态这些每天都在变的字段，除非手动重跑 `insertToDB.ts`，否则永远停在首次抓取的状态。
而 `fetch-ins-daily.ts` 一直是「每次运行都刷新用户信息」（`upsertInsUserInfo`），两条链路的策略不一致。

**做法**（复用已有的写入口，不新增 SQL）：

- 每个用户抓推文前先跑 **Phase 0：刷新资料** —— `apiClient.fetchUserDetailsRaw(user.id)` 拿整份
  `EnrichedUser`（含 `followersCount` / `followingsCount` / `statusesCount` / `description` / `profileImage` 等），
  再交给 `createUser`（`packages/database/modules/user.ts`，`insert ... onConflictDoUpdate`）
  upsert 回 `users` 表。
  - 不用 `updateUser`（纯 `UPDATE`）是因为 `createUser` 是 `insertToDB.ts` 已在用的同一入口，语义一致；
    且 upsert 在「用户行被删/首次出现」时也能自愈。
  - upsert 的 `set` 只覆盖 `restId` + `jsonData`，`daily_fetch` / `ins_username` / `ins_json_data`
    三列不受影响（前者是订阅开关，后两者归 IG 链路维护）。
  - 定位用 `user.id`（restId）而非 userName：改名不影响定位，避免 upsert 出第二行用户。
- **失败分层**：资料刷新失败只记 `refresh-user-error` 日志并继续抓推文 —— 资料是附带产出，推文才是主数据；
  但**Key 级失败（401/403/429）照旧立即中止整轮**，不做「18 个用户各失败一遍」的无用重试。
  该判定抽成 `getAbortReason()`，Phase 0 与 Phase 1 共用（原先内联在 timeline 的重试 `catch` 里）。

**验证**（dev 库，18 个 `daily_fetch` 用户，取第 1 个实跑）：

- 抓取通路：`fetchUserDetailsRaw(user.id)` 用库里的 restId 直查成功，实打实带回漂移值
  （`followersCount` 131,296 → **136,915**、`statusesCount` 1,678 → **1,806**，即这次要修的问题）。
- upsert 语义：`createUser` 前后对比 —— `rest_id` / `userName` 不变、`daily_fetch=true` 保持、
  `ins_username` / `ins_json_data` 原样未动、仍为 **1 行**（没因 conflict target 多出第二行）；
  再读回 `users.jsonData` 已是新值（`followersCount: 136915`）。
- 门禁：`bun run lint:check` ✅（顺手 `eslint --fix` 修了 CLAUDE.md 表格的 prettier 对齐）/
  `bun run typecheck` ✅ / `bun run test` ✅（shared 20 + database 15 + server 38 + web 80）；
  `bunx tsc --noEmit -p apps/scripts/tsconfig.json` 仅剩既有的 `exportTweets.ts:91` 类型错误（与本次无关）。

**影响**：每天多 18 次 `UserByRestId` 请求（每个用户 1 次），相对每个用户 1-N 次 timeline 翻页可忽略。
