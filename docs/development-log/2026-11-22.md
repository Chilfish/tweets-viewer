# 2026-11-22

## IG 每日同步接上代理（issue #20–#22）

11-19 起 `Daily Data Update` 连续三天失败，耗时从 ~1.5 分钟涨到 ~17 分钟。失败点只在 IG 步骤：

```
fetch-tweet-daily   ✅ 18 个用户全部成功
ins-sync（IG）      ❌ 15 个账号全挂 → ok=false → exit 1
```

日志里统一是 `GraphQL: 429` / `REST: 404 … not-logged-in — sessionid is missing or expired`。

### 根因不是 Cookie 过期

用本地 `.env` 里同一份 `INSTAGRAM_COOKIES` 跑项目自己的代码，只换出口：

| 出口 | 结果 |
| --- | --- |
| 本机直连（家宽） | `collectUserPosts` 正常，`ritsu_mgmg` 抓到最新帖 |
| mihomo 香港节点（数据中心） | 报错与 CI 逐字一致 |

`/info/` 经代理能过、`posts` 的 GraphQL 被拒，说明是 IG 对数据中心出口的账号级风控（与 postmortem 006 的 X 403 同类）。

另外，IG 步骤是 11-19 `adbe6e5` 才接进 `dailyUpdate.ts` 的，此前 20 次运行 IG 根本没跑，所以「以前一直绿」不代表 IG 曾经通过 CI。

### 代理没接上

`fetch-daily.yml` 的注释写「所有抓取统一经 mihomo」，但 `TWEET_PROXY` 只传给 `RettiwtPool`（X 专用）；IG SDK 用原生 `fetch`，只认 `HTTP(S)_PROXY`，而 workflow 从未设置过（`git log -S HTTPS_PROXY` 为空）。

## 改用上游 0.3.0 的代理能力

`@chilfish/gallery-dl-instagram@0.3.0` 新增 `createSDK({ proxy })`：显式传入时所有请求走该代理，未传时读取 `http_proxy` / `HTTPS_PROXY` / `https_proxy`，传 `null` 关闭回退。Bun 用原生 fetch 的 proxy 选项，Node 走可选 peer `undici` 的 `ProxyAgent`。

验证：

| 场景 | 结果 |
| --- | --- |
| `proxy: 'http://127.0.0.1:7890'` | 请求确实转发（`/info/` 通过） |
| `proxy: 'http://127.0.0.1:1'`（死端口） | `ECONNREFUSED`，证明选项生效、不会静默回退 |
| 香港节点抓 `posts` | `Rate limit exceeded (code 1675004)` —— 错误从「未登录」变成明确限流码，说明链路已通，剩下的是节点质量问题 |

- **`lib/session.ts`**：`openSession()` 读取 `IG_PROXY`，缺省时回退 `TWEET_PROXY`（与 X 共用同一条出口），显式传 `null` 可关闭；两者都没有时保持直连。
- **`fetch-daily.yml`**：抓取步骤补 `IG_PROXY`（与 `TWEET_PROXY` 同值，指向 mihomo）。
- **媒体下载**：`downloadOne` 的 `fetch` 同样读取环境变量代理，Bun 下自动生效，无需改代码。

> 香港节点当前被 IG 限流（code 1675004）。若持续失败，需要给 IG 单独挑一个能过风控的出口（家宽/住宅类节点），或把 IG 步骤的失败与推文抓取分开上报。
