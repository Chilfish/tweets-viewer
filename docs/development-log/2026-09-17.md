## API 参数校验与媒体分页修复（issue #8 / #9）

冒烟测试 issue #8、#9 的处置（同属「分页元数据 / 参数传递」问题簇）：

- **#8 参数校验错误语义错位**（`apps/server/routes/tweets.ts`）：
  - `noReplies` 从 `dateRangeSchema` 移出，与 `reverse` 共用 `booleanQuerySchema`（接受 `true`/`false`/`1`/`0`），
    不再返回与之无关的 `invalid date range`；`/get/:name` 的 pagination + 日期范围 + noReplies 合并为单一 schema，
    校验失败一次性回传 zod `issues`（`字段: 原因`），不再硬编码区域文案
  - `cursor` 增加 `/^\d{1,19}$/` 校验（snowflake，19 位上限防 BIGINT 溢出）：非法游标返回 400，
    不再透传到 `CAST(... AS BIGINT)` 触发 500
  - `search` 按字段分别报错：`q` 缺失 → `q: keyword is required (1-200 chars)`、超长 → `q: keyword is too long (max 200 chars)`、
    `name` 非法 → `name: invalid name`
  - 未归档用户语义写进 API 文档：单资源 `GET /v3/users/get/:name` → 404；集合/统计端点（tweets get / medias / stats / last-years-today）→ 200 空结果
- **#9.1 medias 日期范围下 total/hasMore 失真**：带日期范围时不再复用未过滤的 `mediaTweetCountCache`
  （缓存 key 只有 `name`），改为交给 `paginateTweets` 按 `whereClause` 重新 count，空页 `hasMore` 收敛为 `false`
- **#9.2 媒体查询性能**：新增 migration `0004_add_media_sortkey_index`，为媒体时间线建 partial index
  `idx_tweets_media_sortkey (userName, COALESCE(retweeted_original_id, tweetId) DESC) WHERE <媒体谓词>`，
  谓词与 `getMediaTweets` 的 whereClause 对齐；并登记进 `_journal.json`

**验证**：`bun run lint:check` ✅ / `bun run typecheck` ✅ / `bun run test` ✅（shared 20 + database 15 + server 38 + web 80）/
`bun run build:client` ✅。

## 线上索引补齐与 `db:push` 根因（线上 102,782 推文 / 20 用户）

复核 #9.2「媒体查询恒定 ~1s」时发现线上 `tweets` 表**只有 `tweets_pkey` + `tweets_tweetId_unique`**：
0001 / 0003 的性能索引全部缺失、`pg_trgm` 未安装，`medias` 查询退化为 Parallel Seq Scan（**Execution 1631ms**）。

- **根因**：`drizzle-kit push` 按 `schema.ts` 对齐数据库，而 schema 当时**未声明任何索引** → push 时被 DROP。
  0001 在 `__drizzle_migrations` 里仍记录为 applied，所以 `db:migrate` 不会重跑、索引再也不会回来。
- **修复**：
  - `schema.ts` 声明全部 5 个查询索引（`idx_tweets_username_createdat` / `idx_tweets_createdat` /
    `idx_tweets_username_sortkey` / `idx_tweets_fulltext_trgm`（GIN，需 pg_trgm）/ `idx_tweets_media_sortkey`（partial）），
    push 不再删除它们
  - `0003` 登记进 `_journal.json`（此前 `readMigrationFiles` 根本读不到它）并补 `--> statement-breakpoint`
    （Neon 的 HTTP 预处理语句不接受多命令批）
  - 新增 `0005_restore_dropped_indexes`，把被 push 删掉的 0001 索引幂等补回
- **结果**：dev + 线上均已 `db:migrate` 应用。线上 `medias` 查询从 **1631ms → 0.18ms**
  （`Index Scan using idx_tweets_media_sortkey`）；dev 上实测 `db:push --force` 后 5 个索引保持不变。
- **部署注意**：线上 worker 的 `DATABASE_URL` 指向 `ep-empty-pine-…`，与本地 `.env`（`ep-old-haze-…`，3 用户）
  不是同一个库。直接 `bun run deploy` 会用本地 `.env` 覆盖线上 worker 的 `DATABASE_URL`——部署前务必确认目标库。
