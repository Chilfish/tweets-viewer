## 滚动续载同步 URL 页码（page 与 cursor 双机制收敛）

**背景（用户实测反馈）**：无限滚动追加下一页时走 keyset cursor 拉取，但 URL `page` 不更新——翻到很后面了 URL 还停留在之前的页面（如始终 `?page=1`），分页器显示也停在锚点页，刷新/分享无法定位当前阅读进度。`page` 与 `cursor` 两个分页机制并存但各管各的，状态载体与实际进度脱节。

**修订决策**：滚动续载仍然 keyset cursor 拉取（4A 深翻页不退化），但每成功续载一页后用 `history replace` 把 URL `page` 同步为**已加载页数**——URL 如实反映阅读进度，且不产生历史记录（返回键不受影响）。`page` 依旧兼任定位锚点（刷新/跳页 → loader 按 page 拉取并替换列表）。

- **`app/lib/paginated-stream.ts`**：`StreamState` 新增 `loadedPages`；`applyLoaderPage` 恒对齐 URL `page`（替换/顺序追加都收敛到 `page`），`applyFetchedPage` 续载成功 `+1`。
- **`app/hooks/use-url-paginated-stream.ts`**：`loadMore` 成功后在**发起时刻 URL 页码未被用户改动**的前提下 `setSearchParams(replace)` 同步 `page = loadedPages`；若续载期间发生了跳页/筛选（URL 被用户接管）则丢弃该次追加/不抢写 URL，避免旧游标续载污染新流、旧页码覆盖新跳页。
- **五条路由（tweets/media/search/last-years-today/ins）**：列表容器 key 从 `searchParams.toString()` 改为 filterKey（`name-reverse-start-end-noReplies` 之类）——滚动同步页码不会再触发整页重挂载闪动（5B-3 的"追加不整屏闪动"保住了）；跳页/筛选变化仍会换 key 重挂载淡入。副作用：纯跳页（页码变化）不再整容器淡入，但新 page 条目各自 `slide-in-from-bottom`，视觉反馈仍在。
- **契约测试**：`paginated-stream.test.ts` 补 `loadedPages` 断言（替换→=page / 顺序追加→=page / 续载→+1）。

文档同步：`docs/Specification.md` §4.2、`docs/planning/architecture.md` ADR-009 后果、`docs/planning/action-plan.md` 登记。

验证：`bun --cwd apps/web-react test` — paginated-stream 9 项 ✅（补 `loadedPages` 断言）；typecheck ✅ lint ✅ build ✅（build 的 prerender 请求超时为沙箱环境问题，与本次无关）；既有 13 项失败为 zustand persist localStorage 环境问题（pre-existing，与本次无关）。

## 视觉回归测试地基（VRT：vitest browser mode + toMatchScreenshot）

**背景**：Phase 5 视觉打磨成果（token 化、双主题、四态统一）没有任何自动化回归防护，现有 61 用例全是行为断言。选型走自托管 Vitest browser mode（`toMatchScreenshot`），不用 Chromatic——storybook addon-vitest 官方不支持该断言（storybookjs/storybook#32930），Storybook 保持工作台角色。方案全文见 `docs/planning/visual-regression-testing.md`。

**落地**（action-plan V1–V5，V6 待 PR 流程）：

- **`vitest.config.ts` 第三 project `vrt`**：chromium headless 1280×720、`*.vrt.test.tsx` 命名约定、1% 像素容差；`test` 脚本收窄为 `--project unit --project stories`，新增 `test:visual`。**三个非显而易见的坑**：① `browser.enabled: true` 必须显式开（v4 默认 false，不开落 forks pool 报「vitest/browser can be imported only inside Browser Mode」）；② 需 `define` 注入 `VITE_API_URL`（`shared/constant.ts` 的 `process.env.API_URL` 兜底在浏览器 iframe 里没有 `process`）；③ 必须挂 `@tailwindcss/vite`，否则 `@import 'tailwindcss'` 不被处理、截图是无样式白板（stories 冒烟只验渲染不炸，从未暴露）。
- **用例**：FeedStatus 四态×双主题（10）+ MyTweet 三形态×双主题（6）+ ProfileHeader×双主题（2）= 18 基线。fixture 图片全用内联 SVG data URL（零网络确定性）；媒体用例 mock `getMediaUrl`（twimg 规则会改坏 data URL）；双主题靠 `documentElement.classList.toggle('dark')`（与产线机制一致）。
- **基线纪律**：CI-only 生成（`--font-sans` 系统栈，win32/linux 渲染必然不同）；`**/__screenshots__/**/*-win32.png` 进 .gitignore；本地 18/18 绿 4.7s。
- **CI**：`ci.yml` 新增独立 `visual` job（playwright `--only-shell` + `fonts-noto-cjk`）；新建 `update-screenshots.yml`（PR 打 `update-screenshots` label 触发，ubuntu 重生成 → 同环境 verify → bot commit 回分支）。**两个 job 环境必须严格同构**，否则基线像素级失配。
- **像素级验证**（本地无图像模型，用 System.Drawing 采样代替肉眼）：light 背景 RGB(245,249,251) 精确命中 `--background: #f5f9fb`、dark 近黑、fixture 填充色大量命中、dark/light 基线哈希不同——确认 Tailwind/token/主题/data URL 全链路真实生效。

验证：`test:visual` 18/18 ✅；`test`（unit+stories）11 files / 61 用例数量不变、vrt 未被吞（002 铁律核对）、13 失败与既有基线逐项一致；typecheck ✅ lint ✅。

**V6 播种与两轮踩坑（PR #7 流程）**：① `git add -- 'app/**/__screenshots__'` 的 pathspec `**` 语义与预期不符（`:(glob)` magic 也救不了，均报 did not match）→ 改宽路径 `git add -A -- apps/web-react/app`（全新 checkout 上唯一变更是基线，安全）；② **`bun --cwd X run <script>` 是无效语法——打 usage 且 exit 0**，visual 门禁与播种 workflow 双双假绿空转两轮才暴露（「全步骤 ✓ 但 bot 说无变更」的矛盾戳穿）→ 全部改 `working-directory:` + `bun run`，已沉淀 [postmortem 004](../postmortem/004-bun-cwd-run-false-green.md)。修复后真实播种成功：regenerate 18 passed → verify 18 passed → bot commit `cb6acef` 携 18 张 linux 基线回分支。教训复述：**CI 的绿必须在日志里看到真实产物，不能只信退出码**。
